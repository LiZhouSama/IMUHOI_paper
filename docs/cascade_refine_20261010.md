# 级联 refine 架构：HP → VC → OT → VC-refine → OT-refine → HP-refine（2026-10-10）

## 0. 目的与结论（结果见 §5）

**结论（2026-10-11）**：级联在 OMOMO、BEHAVE 上都没有超过现有管线。VC-refine 本身有效（接触 F1 提升，同一 OT 上物体
BEHAVE −1.4~−1.7 cm、OMOMO −0.5 cm），但只有"只重融合发布帧"（e1）时有效；用户方案的整窗重融合（e2）和 HP 历史用 refine
值都显著有害；去掉 feedback + joint 的代价（BEHAVE ~2 cm）补不回来。最好的 e1：OMOMO 与现有管线持平，BEHAVE 略差。

用户提出（10-09）：在当前 HP、VC-v5ar、OT v2_armrot_biclose 的基础上，取消 VC+OT joint 训练和 OT state feedback，
改成 `hp -> vc -> ot -> vc-refine -> ot-refine -> hp-refine`。核心是 VC 的纠错：用第一遍 OT/HP 的结果判断 VC
接触是否合理，修正后重新融合物体、再微调人体；在线时 HP/VC/OT 的历史用 refine 后的结果填充。

本文档记录这个架构的隔离实现、与现有管线"平等"的训练/测试协议，以及 OMOMO、BEHAVE 上的结果。
不改动任何原有代码：新代码全部在新目录（`model/cascade/`、`train/cascade/`、`scripts/cascade/`、
`test/test_cascade_refine.py`），对原有模块只做子类化或运行时替换。

## 1. 架构

```
在线窗口 [t-59, t+10]，只发布第 t 帧
① HP（冻结，stage-1）            → 姿态 / 根 / 掌心
② VC-v5ar（冻结，第一遍）         → 接触 logit (L|move, R|move, move)、物体速度
③ OT（v2_armrot_biclose，无 feedback）
     预测器整窗一次批量前向；融合只从已发布历史出发算第 t 帧，并顺延到前瞻帧（给 VC-refine 看）
④ VC-refine（新模块）            → 整窗修正后的接触（残差 logit，零初始化 = 恒等）
⑤ OT-refine（复用 ③ 的权重，用修正后的接触重跑）
     e2（主方案，用户原文"整窗 for 门控融合"）：从"上一窗口 OT-refine 在本窗口起点的值"出发重新融合整窗，发布第 t 帧；
         ③ 的前缀也用上一窗口 OT-refine 的整窗结果（用户原文"基于上一窗口的 ot 结果"）
     e2p（第一版 e2，已证伪，见 §2.1）：从"本窗口起点那一帧当时发布的值"出发重新融合整窗
     e1（消融）：保留已发布前缀，只重融合第 t 帧
⑥ HP-refine：OT 的 refine head，读 OT-refine 的输出（只发布，不回灌）
```

e2 的状态传递（carry）：窗口 t 的 OT-refine 结果 Q_t 覆盖 [t−59, t]；窗口 t+1 的起点状态取 Q_t(t−58)，第一遍 OT 的
前缀（位置、门控权重、FK 滤波状态、接触）取 Q_t 的 [t−58, t]。于是"提交"的轨迹是一条每个窗口前进一帧的链（固定延迟
平滑器），发布帧是从这条链出发、用本窗口的修正接触重融合 58 帧的末端。已验证（单序列插桩）：起点状态与上一窗口的值
逐位相同，发布值就是窗口末端。

历史填充：接触、物体位置、融合权重、v2 FK 滤波状态都用 refine 后的发布值（e2 的 OT 起点改读 carry）。HumanPose 的初值默认仍读 stage-1
历史（`cascade_hp_history: stage1`），因为 refine head 输出近似常数 +2.4 cm 竖直抬升，而在线根积分
`root_t = root_{t-1} + v/fps` 加上只向上的地面修正，会把它逐帧累加（见 [[ot-refine-head-effect]]）；
用户原文的"HP 历史也用 refine 值"作为消融 `cascade_e2_final_hprefined` 评测。

**VC-refine 的输入（每帧，56 维，`model/cascade/vc_refine.py`）**：VC 第一遍的 logit/概率；物体 IMU（物体系速度、
|a|、角速度、静止门）；每只手的 (a) 判断前状态几何：手 → 上一帧融合物体的物体系向量与长度，(b) 无状态 FK 候选的
骨向量，(c) 候选新息 FK − 上一帧状态，(d) FK 候选速度与 VC 物体速度之差、掌心速度与物体速度之差；双手 FK 候选
分歧、掌心间距、双手闭合候选 − 状态；融合轨迹速度及其与 VC 速度之差。双向 GRU（2×128）看整个在线窗口（窗口止于 10 帧前瞻）。

**发布与评测器的关系**：评测器对发布物体做"用 refine 后掌心重放四路融合"（`_build_published_object_trans`），
逐帧接着自己的上一帧算。这对原协议和 e1 是精确的，但 e2 每帧都从窗口起点重新融合，逐帧重放表达不了。因此级联
在每个窗口内自己做同样的掌心修正（`publication_chain`），把它作为 `pred_obj_trans` 发布，并隐藏评测器重放用的
候选键，让评测器直接评级联自己的发布轨迹；循环内部用的未修正轨迹保留为 `cascade_raw_obj_trans`。
已验证：VC-refine 取恒等、e1 时，级联与"无 feedback OT + 原在线循环"的评测结果逐项一致（物体发布误差完全相同，
HOI 差 1e-6）。

## 2. 实现中发现的问题：无 feedback + biclose 的原训练路径

`ObjectTransModule._scan_predictor` 在无 feedback 时走向量化路径：LSTM 整窗一次前向，但融合循环里传给双手闭合门控的
"当前帧预测器隐状态"始终是初始状态（循环里从不步进 LSTM）；而在线推理走逐帧步进路径，用的是真实的每帧隐状态。
训练和推理不一致。现有结果不受影响（所有 biclose 运行都开着 feedback，走逐帧路径）。级联的 OT
（`model/cascade/ot_nofb.py::CascadeObjectTransModule`）在批量前向时保留每帧顶层隐状态并逐帧传给门控；
`test_scan_matches_stepped_lstm_reference` 验证它与逐帧步进的参考实现一致，
`test_stock_vectorized_nofb_path_hands_the_gate_the_initial_state` 记录原路径的差异。

### 2.1 第一版 e2（现名 e2p）的结构性错误：59 条交错的链

第一版 e2 从"窗口起点那一帧当时发布的值" P(t−59) 出发重融合整窗，于是 P(t) 只依赖 P(t−59)，P(t+1) 只依赖
P(t−58)：发布轨迹实际上是 59 条互不相干、按帧交错的链，每条链各自累积漂移，相邻帧属于不同的链。BEHAVE 全量评测
（VC-refine final）：物体抖动（每帧二阶差分模长）中位数 57 mm、最长序列 348 mm，B0 只有 7 mm；抖动与序列长度
秩相关 0.39（B0 0.07）。物体误差反而比 B0 低 1.2 cm，但这个轨迹不能用（每帧几厘米到几十厘米的来回跳）。
冒烟测试只用了 2 条短序列，抖动只翻倍，没有暴露这个问题。修正为上面的 carry 版本，旧版本保留为 `e2p`
（`cascade_e2p_final`）以记录这一失败。

修正后的 e2 仍有内在抖动：同一帧在相邻两个窗口里被重融合的位置平均相差约 1.2 cm（p90 约 2 cm，窗口第 5 帧以后
基本不随位置变化），而接触概率的修订很小（平均 |Δp| 0.03）。主要来源是 OT 预测器每个窗口从头运行，同一帧在不同
窗口里的预测不同，整窗重融合把这些差异带到发布的末端帧（plasticcontainer 单序列：e2 抖动 19 mm，B0 7.9 mm）。
这是"每帧重融合整窗、只发布末端"这一结构本身的代价，不是实现错误。

## 3. 训练协议（与现有管线对齐的部分 / 不同的部分）

| 阶段 | 现有管线（基线） | 级联 |
|---|---|---|
| HP | 复用 checkpoint | 同一 checkpoint |
| VC | v5ar 独立训练 → joint 阶段与 OT 一起微调 | v5ar 独立训练的同一 checkpoint（joint 之前），冻结 |
| OT | v2_armrot_biclose，feedback 开，OT 阶段 + joint 阶段 | 同一配置文件，只改 `object_trans_state_feedback: false`，只有 OT 阶段（B0）。用原训练脚本，只替换模块类 |
| 第二阶段 | joint（VC+OT，lr×0.1） | VC-refine（新模块从头训练，HP/VC/OT 冻结），沿用 OT 阶段的 epoch、里程碑、评估间隔、早停规则和 lr |
| HP refine | OT refine head（OT 阶段训练） | 同一个 head（B0 训练），作用在 OT-refine 的输出上 |

共同点：同一份数据和窗口（60 帧，batch 800，每序列 4 窗）、同样的 Noitom 噪声（seed 42）、同样的 schedule 缩放和早停、
best（测试集窗口 loss 选）和 final 两个 checkpoint 都评测；评测用原 `eval_batch_online.py`（窗口 60 + 前瞻 10、
差分速度初值、HP 平滑 7、仿真 IMU 噪声 seed 42），通过 `scripts/cascade/eval_cascade_online.py` 只替换模型。
基线用同一包装重新评测（结果与原 JSON 逐位一致），以便逐序列配对。

**VC-refine 的训练设计（新模块，需要说明的选择）**：
- 损失：主项是 VC 的接触损失（obj_move、手接触条件 BCE、边缘 BCE，沿用 VC 的正/负/硬负样本权重）；辅项是 OT-refine
  输出的位置误差（全部帧的物体 L2 × 0.5，GT 接触帧的 HOI × 0.5/手），梯度经固定融合权重和预测器接触输入回传。
  没有沿用 OT 的 obj MSE×5 + HOI×10：那样 HOI 项约为接触损失的 10 倍，且只评 GT 接触帧，等于鼓励多接触、看不见拖拽。
- 窗口起点状态噪声：80% 的窗口把两遍 OT 的起点物体位置加 σ·N(0, I)，σ（每轴）在 [2, 30] cm 对数均匀。
  原因：在线时判断依据的状态有漂移（发布物体误差 BEHAVE 中位数 22 cm、OMOMO 12 cm），只用 GT 起点训练会让 VC-refine 过度信任几何。
- 合成 VC 错误：50% 的窗口在 VC 第一遍 logit 里写入一处错误（假接触段——静止物体上同时抬高 move logit、漏接触段，
  或单手轨迹平移 3–12 帧），再跑第一遍 OT，让第一遍带上错误接触造成的拖拽。原因：VC 在自己的训练窗口上太准，
  只靠样本内错误学不到纠错（BEHAVE 在线 F1 训练 0.955 vs 测试 0.90）。

### 5.4 结论

1. **级联在两个数据集上都没有超过现有管线。** 最好的形态 e1 在 OMOMO 上与现有管线持平（物体 −0.12、HOI +0.16，均不显著），
   在 BEHAVE 上略差（物体 +0.3~+0.6 不显著，HOI +1.0~+1.1，best 显著）。
2. **VC-refine 本身有效。** 接触 F1 提升（BEHAVE 0.873→0.897，OMOMO 0.960→0.967~0.970）；在同一个 OT（B0）上只用于发布帧
   （e1）时，物体误差 BEHAVE −1.4~−1.7 cm、OMOMO −0.5 cm（显著），收益主要在非接触帧（BEHAVE 25.1→22.3 cm），
   即修正误判接触造成的拖拽。但它补不回去掉 state feedback + joint 的代价（BEHAVE +2.0/+1.4，OMOMO +0.34/+0.27）。
3. **用户方案的核心"OT-refine 整窗重融合"（e2）有害。** 不开 VC-refine，只做整窗重融合，就让 B0 变差（BEHAVE +1.0/+2.0，
   OMOMO +1.2/+1.25），抖动 2~5 倍。原因：每帧都从一条"提交链"出发重融合 58 帧，而提交链每一步用的是窗口第 2 帧的
   预测器输出（LSTM 几乎没有上下文）；同一帧在相邻窗口被修订约 1.2 cm；加上 VC-refine（双向 GRU）对同一帧的接触
   在窗口间翻转（yogaball_sit 平均 |Δp| 0.30），整窗重融合把翻转放大成发布帧的跳变（该序列抖动 149 mm）。
4. **HP 历史用 refine 值有害。** 根误差 16.3→26.9 cm，物体 +5~+6 cm（refine head 的竖直抬升被在线根积分逐帧累积）。
5. **e2p 的教训：** 冒烟测试只看 2 条短序列不足以发现随序列长度累积的结构问题；以后改在线状态传递时，至少要检查
   抖动与序列长度的关系。

**如果还想继续这个方向，最短路径**：保留 state feedback 和 joint，只在现有管线上加 e1 式的 VC-refine（用第一遍 OT/HP 几何
